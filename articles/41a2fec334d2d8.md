## tscからtsgoへ ── DenoのTypeScript基盤はどう変わったか（maguro）

https://2026.tskaigi.org/talks/2

- 今回見るのは`deno check`(型チェック、LSPも含む)。
- Denoのソースにはstock TypeScriptだけでは決められない要素がある。(Denoという名前空間はtscの標準型定義にない)
  - 診断パス(deno run)でTSが扱える形に変える必要ががある。
    - import mapsやreadFileなどのDenoAPIといったもの。
  - 一方で実行パス(deno check)では型注釈を剥がしspecifier(import "x" from "y"の"y"の部分)を解決してからV8に渡す。
    - ここにtscやtsgoは介入しない。
- TypeScript checkerとlanguage serviceをどうDenoのmodule worldと接続してきたか。
  - フェーズ1「embedded tscベースのアーキテクチャ」
    - tscをV8で動かし、ファイル読み込み、モジュール解決などをDeno Rust側で行う。
    - tscに近い挙動を保ちやすい。
    - 一方tscのバンドルサイズが大きく、tsc用のruntimeなどを作る手間がかかりコストが大きい。
  - フェーズ2「forkd tsgo subprocess」
    - tsgoを試す実験的な機能として`--unstable-tsgo`オプションが追加。
      - 対象は`deno check`のみ。
      - 公式のtypescript-goを採用せず、denoland/typescript-goをフォーク。
        - Deno固有の概念をtsgoに渡すため。
        - ただしTS本体との差分を背負う必要あり
    - tsgoはDenoのspecifierやmodule graphをそのままでは解決できないため、型チェック中にtsgoがDeno側に聞きに行くcallbackを返すようにした。
      - Rustからchild processを通してtsgoへ。
- LSP(エディタ補完)はどうするか
  - deno checkと異なりエディタを開いている間ずっと動かす必要があり、キャンセルなどの状態も管理しないといけない。
  - フェーズ3「forkを捨てて、npmパッケージへ」
    - フェーズ2でやったtsgoのフォークを撤回。
    - tsgoをremoveし、公式のTypeScript(npm)に寄せる形式に変更。
      - つまりTSにDenoの定義を追加する形式をとった。
    - stock TypeScript向けに型をローカル生成する。
      - つまりtscやtsgoを介さず翻訳を試みる。
      - DenoのTypeScript checkerが公式と同じ動きをするように。

Denoの裏側を今回初めて知りました。
Denoの独自ルールが結構ある印象だったので、型チェックは独自ものを採用しているのかと思っていたのですがまさかのtscに読み取らせる形式をとっていたとは思いませんでした。
tsgo対応はnode_modules内に型定義ファイル書き込む方式
で解決していている一方、oxlintやvizeは別のアプローチをとっていて各種OSS大変そうだなという印象を受けました。

## TypeScriptの「型」をAIのスキルに昇華させてみた件について（higak9）
https://2026.tskaigi.org/talks/7

- AIの型知識チェック
  - プロンプト「TSの型について知ってる分だけ全て教えてください。」
  - 「Awaited Types、Template Literal Typesはどんなものが答えられるか」
  - 「TypeScriptの型と集合論の関係について」 
    - これら全て問題なく回答。TSの基本知識は問題ない。
- 型表現によってAIの解釈も変わるのか。
  - string より "left" | "right" | "center" のようなリテラル型の方が、AIが正確に意図を読む。
  - any を乱用したコードは人にもAIにも悪影響。
  - 高度な型（Branded Types / Discriminated Union / Mapped Types）を使ったコードと基本型だけのコードを比較してAIに分析。
    - 前者の方が正確かつ具体的に仕様やリスクを読み取ることができていた。
- 型からスキルに昇華
  - tscAPIで型定義から自動でAIスキル（JSON Schema）を生成
    - AST解析からメソッド・パラメータ・戻り値を抽出
    - Union型をenum、Branded Typesを検出してJSON Schemaに変換しスキル定義を生成する
      - これを元にバリデーション・テスト・CLI・APIドキュメント・MCPツールが生成される
- 型の書き方一つの工夫が、AIの解釈に大きな差を生む。Compiler APIとAIの組み合わせは相性が良く、引き続き実験価値がある。

型情報からMCPまで落とし込むことまで行けることに驚きです。
ドメイン情報を型に落とし込むことである程度AIが機械的に自走してくれるようになるのではないかなと思いました。

## 制約と時代から読み解くTypeScriptコンパイラ設計史（Yoshiaki Togami）
https://2026.tskaigi.org/talks/38

- 1年前tsgo発表
- tsgoはなぜGoか
  - tscはAST・Symbol間に循環参照を抱え、ASTがセマンティック情報を直接背負う独特な設計
  - JS環境の制約（メモリレイアウト制御不可、Worker APIなし）のもとでイミュータブルを諦めた結果
  - GoはStructのインライン埋め込みと共有メモリ・マルチスレッドが使えるため相性が良い
    - またclassが使われていなかった点も大きい

- TSコンパイラの処理フロー
  - Source → Scanner → Parser → Binder（ASTとSymbolを結合）→ Checker（型を計算・検査）
  - 問題はBinderで、ASTとSymbol間の双方向参照（循環参照）が複雑に絡み合っている
- なんでこうなったか歴史を紐解く
  - 2004年Gmail・2005年Google MapsでAjax革命、2008〜2009年にV8/Chrome/Node.js登場
  - 2010年MicrosoftはOfficeのWeb移植のためJS大規模開発が必要に。JS環境が貧弱すぎてエディタから作ることに
    - このエディタが後のVSCodeとなる
  - JSを遠ざける・置き換えるより「JSのスーパーセット」として型を作る方針に
    - TSの誕生
  - エディタ要件（200ms以内の応答、局所変更）でRoslynのRed-Green Treeのような理想設計は断念
  - 結果、単一AST＋Binderで段階的に情報を詰め込む設計に（イミュータブル放棄）

- GoポートでJS時代の制約が解消
  - ネイティブバイナリ化（×3倍）＋共有メモリ・マルチスレッド化（×3倍）で合計×10倍の高速化
  - Goの値型でフィールドをインライン埋め込み→キャッシュミス削減
  - JSの共有メモリの煩雑さ（SharedArrayBuffer等）も解消

TS開発の背景と一緒にコンパイラの歴史も振り返りました。
JSの大規模開発用として作られたのがTSというのだけ知っていて、「Office製品のWeb移行」「JSが貧弱だったのでエディタから作り、それが後のVSCodeとなる」というのは初耳でした。
コンパイラとしても、当時のJSやメモリが貧弱で苦しい部分も多く、なんとかイミュータブルを放棄して再現したものの、JSの限界が来ていたことがよくわかりました。
本当に茨の道だったんだなTypeScript...

## Real World Effect-TS: 堅牢なプロダクトを型で組み上げる（asa1984）
https://2026.tskaigi.org/talks/50

- TSバックエンドは中規模以上の開発に耐えられるか
  - 規約的フレームワークが不在（RailsやLaravelに相当するものがない）
  - 解決策として関数型ドメインモデリングを採用
    - Errors as Values / 副作用の分離 / ワークフローの合成
  - ここでEffect-TS：「WebフレームワークよりTypeScriptのフレームワーク」
    - エラーハンドリング・DI・非同期処理を型レベルで統一的に扱う

- Effect-TS：`Effect<A, E, R>`
  - A=成功値 / E=エラー / R=依存（Requirements）
  - `Effect.gen()`でasync/awaitのように手続き的に書ける

  - エラーハンドリング
    - `yield*`するだけでエラー型がEチャネルにunionとして合成される（失敗側のレールを自動分岐）
    - Expected（ドメインエラー）とUnexpected（インフラエラー）を区別
      - 型に乗せるのはドメインエラーのみ。インフラエラーは想定外として扱う。

  - DI
    - Tag（識別子+インターフェース）とService（実装）で表現
    - Layerパターンで依存関係グラフを型で表現
    - RがneverでないとエラーになるためコンパイルTime時に依存漏れを検出できる

  - Fiber Scheduler（独自非同期ランタイム）
    - Structured Concurrency：親Fiber終了時に子Fiberを自動終了
    - キャンセル伝播・リソースリーク防止

- トレードオフ
  - 「心中ライブラリ」と呼ばれるほど侵襲性が高い（一度入れると剥がすのが困難）
  - 発表者自身もHERP AI Recruiterへの採用は見送った（fp-ts採用時の負債化経験から）
  - 素のTSで統制を保つ選択肢（高階関数DI、AsyncLocalStorageなど）も有効

思想はまさに関数型で、Reactなどのフロントエンド設計の思想をほぼまま適応できる感じな気がしました。
特にExpected（ドメインエラー）とUnexpected（インフラエラー）の部分で、型に乗せるのはドメインエラーのみというエラーを外的要因と内側な要因に分けている点が印象的で、開発者にかなり委ねられているなーと思いました。


## AI時代に考える、Branded Typesで実現する堅牢な型付け（池奥裕太/@yuta-ike）
https://2026.tskaigi.org/talks/62

- なぜ型を書くのか?
- どんな時？
  - 実装が間違っていた時
実装があっていて、型チェックが通らない場合
- 複雑でTSの方推論が通らない
- 病むおえずミュータブルな処理をする場合(let,最大にゅう,record<string, any>)
  - フォローしてあげる
- 実装が間違っていて、型チェックが通らない
  - これは避けたい。
  - しかしほぼ無理
    - addでreturn 0してるなど
- それでもエラーにしたい
  - BrounefdTyepで実際に活用することで堅牢なアプリケーションになる
- 同じ構造の型をTSは同じものと認識する。
  - これを可能な限り避けたい。
  - そこで型の名前に仮想プロパティを入れることで区別させる
    - これがBranded Types

- プロダクトに載せるとすると
  - ドメインモデルの区別
    - UserIDとUserNameは別の概念だが、我々はどう区別しているか
    - 変数名で区別しているが、stringと定義した場合TS上では同じものになる
    - string & { __type: "UserID" }と宣言することで型レベルで表現が可能
    - 言い換えればビジネスドメインを型に埋め込む行為
  - 状態や属性
    - GitHubのようなのようなユーザー名を指定して登録できるとする。
      - 入力値がstringか
      - ユーザー名の要件を満たすか正規表現チェック
      - DBに保存
      - ユーザー名は文字+数字の場合もはいるが、これも型として表現したい。
        - ValidAsUserNameを定義しここでバリデーションと戻り値を定義。
        - こうすることでDB側に保存する際の検証を事前に行うことができる。
        - また型追跡も有効なので情報が途絶えない。
- 所管
  - 型チェックが通った場合とりあえず安心できる
  - 実装の考慮もれが型エラーで検出できるので気付きやすい
  - 一方で状態や属性の場合asで表現しないといけない場合があるため注意が必要。

ドメインを型定義で表すのがすごく意欲的だなと思いました。
一見プロパティ名が異なっていても、型が同じであればコンパイラとしてはほぼ同じなのは確かに〜って思いましたし、そこにBranded Typesがしっかりと役割を果たしていてすごく綺麗でした。
また本来であればUserID,UserNameのstringもしっかりと型を区別すべきというのも思想として納得がいきました。

## 次世代リンターで探る、tsgo 時代における型認識カスタムルールの現実解（Yuta Takahashi）
https://2026.tskaigi.org/talks/65

- tsgo時代に型認識カスタムルールにどう向き合うか
- 型認識カスタムルール
  - @typescript-eslint/no-floating-promises
    - 式の方がthenableかを見る
   - eslint-plugin-neverthrow/must-use-result
     - resultが処理されず残るのを検出
  - 現在はtypescript-eslintが担う
- tsgoでどう変わるのか
  - tsgoでは方情報のアクセス境界がわかる
  - 型チェック自体がGoのバイナリになるので介入が難しくなる
  - どうするか
  - 既存のts-eslint
    - 公式で併用可能なものが配布されている
  - その他の解析基盤
    - 方チェック自体がtsgoに以降できるのではないか
    - oxlintの例がある
      - 59の互換
      - oxlintはtsgolintをバックエンドにして型認識lintに対応
      - しかし型認識カスタムルールに非対応
    - Rslint
      - 129の互換
      - Go生リンターとして型認識リントに対応
      - カスタムルールと型認識カスタムルールに非対応
      - Goで書いてビルドすることで実質カスタムルールに対応することが可能
    - Biome
      - 16件
      - 独自型推論
- Rslintにパッチを当てて型認識カスタムルールを実装してみる
  - 題材:no-discarded-contract-value
  - 型を捨てているか確認する。
  - internal/rulesに追加
- 書けるだけでは運用モデルに差が出てきて代替えができない
  - Goを書かないといけない&ビルドの手間がかかるので運用負荷が非常に高い。
- 現実解
  - 型認識カスタムリントの向き合い方を再考する
    - 現状のルールで足りるか
    - 型を見ない形に寄せる？
    - 速度がボトルネックか？
    - API対応待てる？
- PoCを型判定からAPI規約に変更
  - importパスやファイル名をAPI協会を識別する
  - 消費関数で扱い方を固定する(TSで縛る)
  - ファクトリ関数でインターフェースを強制する
