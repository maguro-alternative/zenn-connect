## tscからtsgoへ ── DenoのTypeScript基盤はどう変わったか（maguro）

https://2026.tskaigi.org/talks/2

- 今回見るのは`deno check`(型チェック、LSPも含む)。
- Denoのソースにはstock TypeScriptだけでは決められない要素がある。
  - 診断パス(deno run)でTSが扱える形に変える必要ががある。
    - import mapsやreadFileなどのDenoAPIといったもの。
  - 一方で実行パス(deno check)では型注釈を剥がしspecifier(import "x" from "y"の"y"の部分)を解決してからV8に渡す。
    - ここにtscやtsgoは介入しない。
- TypeScript checkerとlanguage serviceをどうDenoのmodule worldと接続してきたか。
  - フェーズ1「embedded tscベースのアーキテクチャ」
    - tscをV8で動かし、ファイル読み込み、モジュール解決などをDeno Rust側で行う。
    - tscに近い挙動を保ちやすい。
    - 一方tscのバンドルサイズが大きく、tsc用のruntimeなどを作る手間がかかりコストが大きい。
  - フェーズ2「forkd tsgo subprocess」
    - tsgoを試す実験的な機能として`--unstable-tsgo`オプションが追加。
      - 対象は`deno check`のみ。
      - 公式のtypescript-goを採用せず、denoland/typescript-goをフォーク。
        - Deno固有の概念をtsgoに渡すため。
        - ただしTS本体との差分を背負う必要あり
    - tsgoはDenoのspecifierやmodule graphをそのままでは解決できないため、型チェック中にtsgoがDeno側に聞きに行くcallbackを返すようにした。
      - Rustからchild processを通してtsgoへ。
- LSP(エディタ補完)はどうするか
  - deno checkと異なりエディタを開いている間ずっと動かす必要があり、キャンセルなどの状態も管理しないといけない。
  - フェーズ3「forkを捨てて、npmパッケージへ」
    - フェーズ2でやったtsgoのフォークを撤回。
    - tsgoをremoveし、公式のTypeScript(npm)に寄せる形式に変更。
    - stock TypeScript向けに型をローカル生成する。
      - つまりtscやtsgoを介さず翻訳を試みる。
      - DenoのTypeScript checkerが公式と同じ動きをするように。

そもそもDenoがtsc使ってることに驚きでした。

## Real World Effect-TS: 堅牢なプロダクトを型で組み上げる（asa1984）
https://2026.tskaigi.org/talks/50

- TSバックエンド中心
- TSバックエンドは中規模以上の開発に耐えられるのか
  - 動くものは作れるが規模が大きくなった時に耐えられるか
  - 多言語との差分
  - 課題:フレームワークが不在
    - RailsやLaravelなどがない。
    - NestJSがギリな状態。
  - 言語本体で頑張る。
    - 型システムの表現力が高い
    - Classが微妙
    - 関数型ドメインモデリングを採用。
      - 型でドメインモデリング
      - Errors as Valude
      - 副作用を分離する
      - ワークフローに合成する。
  - 課題:言語機能と制約
    - 後発の言語に比べて制約が緩い
    - ここでEffect-TS
  - WebフレームワークというよりTypeScriptのフレームワーク。
    - エラーハンドリング・DI・非同期処理を型レベルで統一的に扱う

  - Effect-TS
    - npmパッケージあeffect
    - 独自の非同期ランタイムを型で定義
      - Effect<依存,エラー,リザルト>
      - Effect<A>
        - Effect.get()で手続的にコードが書ける
        - コールバック地獄を回避
        - とりあえずasync/awaitで良いらしい
    - エラーハンドリング
      - yield*するだけでエラー型はEチャネルにunionとして合成される。
        - 失敗側のレールを勝手に分岐させてくれる
        - neverthrowにも似たsafeTryもある
          - Effect-TSはそれに閉じずDIも可能で細かいオプションをつけることが可能。
        - ライブラリからはスルーされるじゃん
          - Effect-TSはExpocted(ドメインエラー400)とUnexpected(500インフラエラー)の2種に区別する。
          - ドメインエラーのみ型に乗せて表現する。
          - つまりインフラエラーは想定外とする。
        - Effect-dieで例外を握りつぶすことが可能。
          - スルーするか否か開発者に委ねる
    - DI
      - 高階関数
        - シンプルだけどネスト時にバケツリレーが発生
      - DIコンテナ
        - 依存をフレームワークが自動で解決する
        - 実行時に解決するため順番の予想がつかない
      - Effect
        - Effect<A,E,R>のR
        - Rがneverじゃないとエラーになる。
      - Requirementの伝搬
        - 自動でunionで構成されるため、結果的に依存注入が不足していると型エラーになる
      - Fiber Scheduler
        - Primiseを高機能で制御したい(Abortでのキャンセルなど)
- 心中性が高いのでリスク
  - 導入するとEffect-TS以外の採用がむずい
  - 完全に負債とかしてしまう場合がある


## AI時代に考える、Branded Typesで実現する堅牢な型付け（池奥裕太/@yuta-ike）
https://2026.tskaigi.org/talks/62

- なぜ型を書くのか?
- どんな時？
  - 実装が間違っていた時
実装があっていて、型チェックが通らない場合
- 複雑でTSの方推論が通らない
- 病むおえずミュータブルな処理をする場合(let,最大にゅう,record<string, any>)
  - フォローしてあげる
- 実装が間違っていて、型チェックが通らない
  - これは避けたい。
  - しかしほぼ無理
    - addでreturn 0してるなど
- それでもエラーにしたい
  - BrounefdTyepで実際に活用することで堅牢なアプリケーションになる
- 同じ構造の型をTSは同じものと認識する。
  - これを可能な限り避けたい。
  - そこで型の名前に仮想プロパティを入れることで区別させる
    - これがBranded Types

- プロダクトに載せるとすると
  - ドメインモデルの区別
    - UserIDとUserNameは別の概念だが、我々はどう区別しているか
    - 変数名で区別しているが、stringと定義した場合TS上では同じものになる
    - string & { __type: "UserID" }と宣言することで型レベルで表現が可能
    - 言い換えればビジネスドメインを型に埋め込む行為
  - 状態や属性
    - GitHubのようなのようなユーザー名を指定して登録できるとする。
      - 入力値がstringか
      - ユーザー名の要件を満たすか正規表現チェック
      - DBに保存
      - ユーザー名は文字+数字の場合もはいるが、これも型として表現したい。
        - ValidAsUserNameを定義しここでバリデーションと戻り値を定義。
        - こうすることでDB側に保存する際の検証を事前に行うことができる。
        - また型追跡も有効なので情報が途絶えない。
- 所管
  - 型チェックが通った場合とりあえず安心できる
  - 実装の考慮もれが型エラーで検出できるので気付きやすい
  - 一方で状態や属性の場合asで表現しないといけない場合があるため注意が必要。
